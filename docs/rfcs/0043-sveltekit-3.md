# RFC-0043: SvelteKit 3, with the origin fixed at build time and the Cloud Run adapter 2.0.0

## Summary

GenoaCMS builds on SvelteKit 2.53, Vite 7 and Vitest 3. SvelteKit 3.1.1 removes what core and the
Cloud Run adapter depend on (`build.md` F21 to F27): `svelte.config.js`, `$lib`, the adapter API's
`generateManifest` and `config.kit`, and, in adapter-node 6, the runtime `ORIGIN`. The author's
decisions are U15 to U19 (2026-10-30). This RFC:

1. **Moves SvelteKit's config into core's `vite.config.ts`** (D10). `@genoacms/config/load`'s
   `resolveKitAdapter` becomes `resolveKitTarget`, which returns the adapter and the origin.
2. **Fixes the origin at build time on every target** (D11, U16). Deployment descriptors gain an
   optional `origin(options)`. The `gcp` and `aws` descriptors return their `origin` option, and no
   longer set `ORIGIN` on the function (DEP-1, DEP-14, LMB-1, LMB-10).
3. **Rewrites the Cloud Run adapter for SvelteKit 3** as 2.0.0 (U18, U19): one bundling pass inside
   Vite's server build, as adapter-node 6 does, the server from `generateServerInstance`, the origin
   from `paths.origin`, no polyfills, and a refusal to start when `ORIGIN` is set (ADP-2 to ADP-5,
   ADP-7, ADP-8). It drops Rollup and its `files/` build step, which also removes `configuration.md` F17.
4. **Migrates core's imports**: `$lib` to `#lib` (U17), `$app/environment` to `$app/env` (D8), and
   what SvelteKit 3 moved or retyped (F28).
5. **Raises the toolchain** in every package that builds or tests with SvelteKit or Vite: Node
   ≥ 22.17, TypeScript 6, Vite 8, `@sveltejs/vite-plugin-svelte` 7, Svelte ≥ 5.57.1, Vitest 4,
   `@sveltejs/adapter-node` 6 (F26).

**Amendment, 2026-10-30: core builds from its published package (`cli.md` LF19, `build.md` D12,
F31).** Core 0.5.0, released from this RFC, fails `genoa build` in every project that installs it.
Its `vite.config.ts` imports `@vitest/browser-playwright`, a devDependency, for §3's browser
provider; and it lists `@sveltejs/kit` only in `dependencies`, so SvelteKit 3 does not treat its
`*.remote.ts` modules as remote functions once core sits in `node_modules` (F31). CI built core only
in place. The amendment:

6. **Moves Vitest's configuration into `packages/core/vitest.config.ts`**, which extends the Vite
   config, so `vite.config.ts` keeps only what a build needs (§8).
7. **Adds `@sveltejs/kit` to core's `peerDependencies`** (§8).
8. **Adds CLI-21 and its end-to-end test**, which packs the packages, installs them with pnpm into a
   fresh project without devDependencies, and runs `genoa deploy` and `genoa build` there. It runs
   in CI's `e2e` job. Released as `@genoacms/core` 0.5.1.

## Specification

The statements' new text is in the architecture documents, committed before this RFC (`8c4050f3`).
What follows is what the implementer needs beyond it.

### 1. `resolveKitTarget` (`@genoacms/config/load`)

```ts
interface KitTarget {
  /** The target's SvelteKit adapter instance; undefined when the config declares no target. */
  readonly adapter: KitAdapter | undefined
  /** The descriptor's origin for the target's options; undefined when it declares none or returns none. */
  readonly origin: string | undefined
}
declare function resolveKitTarget (request: KitAdapterRequest): Promise<KitTarget>
```

It chooses the target exactly as `resolveKitAdapter` does today, with the same errors
(`config/unknown-target`, `config/no-deployment-target`). With no targets it resolves to
`{ adapter: undefined, origin: undefined }`. `origin` is `descriptor.origin?.(entry.options)`, called
with the unresolved options, as `svelteKitOptions` is. `resolveKitAdapter` is removed, not kept as an
alias.

### 2. `DeploymentDescriptor.origin` (`@genoacms/contracts`)

```ts
interface DeploymentDescriptor<O extends object> {
  // … unchanged members …
  /** The origin the built app is served at, given to SvelteKit as `paths.origin`. Receives unresolved options. */
  readonly origin?: (options: O) => string | undefined
}
```

The `gcp`, `aws` and `adapter-node` descriptors: `origin: options => options.origin`. The
`adapter-node` target's options gain `origin?: string` (U20, F30), which `validate` accepts when it
matches `/^https?:\/\/[^/\s]+$/`, and otherwise reports
`origin must be an absolute http(s) origin such as 'https://cms.example.com'`, as the `gcp` target does.

Core's end-to-end harness (`packages/core/e2e/`) builds with that origin: `buildCore()` chooses a free
port, builds with `GENOACMS_E2E_ORIGIN=http://localhost:<port>`, which `genoa.config/e2e.ts` passes as
the `local` target's `origin`, and provides the origin to the test files. `startServer` serves on that
port and no longer sets `ORIGIN`.

### 3. Core's `vite.config.ts`

```ts
import { sveltekit } from '@sveltejs/kit/vite'
import { vitePreprocess } from '@sveltejs/vite-plugin-svelte'
import { readGenoaEnvironment, resolveKitTarget } from '@genoacms/config/load'
// … the existing imports …

const { root, file, target, mode } = readGenoaEnvironment('development')
const kit = await resolveKitTarget({ root, file, target, mode })

export default defineConfig(async ({ mode: viteMode }) => ({
  plugins: [genoa(), tailwindcss(), await sveltekit({
    preprocess: vitePreprocess(),
    adapter: kit.adapter,
    paths: { origin: kit.origin },
    experimental: { remoteFunctions: true }
  })],
  // … the rest unchanged …
}))
```

`readGenoaEnvironment('development')` keeps today's fallback for `svelte.config.js`: the fallback
matters only when `GENOA_MODE` is unset, and the CLI and core's `build` script always set it.
`paths.origin` is omitted, not set to `undefined`, when `kit.origin` is `undefined`, if SvelteKit's
validation refuses an explicit `undefined`. The `vitest` browser project uses
`provider: playwright()` from `@vitest/browser-playwright`, as Vitest 4 requires, in
`vitest.config.ts` since the amendment (§8).

`kit.adapter` is given to `sveltekit()` as `kit.adapter as Adapter | undefined` (`import type { Adapter }
from '@sveltejs/kit'`): `@genoacms/contracts` types a SvelteKit adapter structurally, without SvelteKit,
and its `adapt(builder: never)` is not assignable to SvelteKit's `Adapter`.

### 4. Core's imports

- `package.json` gains `"imports": { "#lib": "./src/lib/index.ts", "#lib/*": "./src/lib/*" }`. If
  core has no `src/lib/index.ts`, the `#lib` entry is left out.
- `tsconfig.json` extends `$app/tsconfig` instead of `./.svelte-kit/tsconfig.json`, and no longer
  includes `.svelte-kit/ambient.d.ts`, `env.d.ts` or `non-ambient.d.ts` (F28).
- Every `$lib/<path>` specifier, including those inside `vi.mock`, `vi.importActual`, `import()` and
  `import type`, becomes `#lib/<path>` with the file's extension: `.js` for a `.ts` module (as
  TypeScript resolves it), `.svelte` and `.svelte.js` as written. `npx sv migrate sveltekit-3` MAY do
  this; the result is checked by the build, `svelte-check` and the tests, not trusted.
- `$app/environment` becomes `$app/env` in `hooks.server.ts`, `host.server.ts`,
  `database/database.server.ts` and its test.
- The types SvelteKit 3 moved are imported from their new modules: `SubmitFunction` and
  `ActionResult` from `$app/forms`, `Handle` from `@sveltejs/kit/hooks` (F28).
- `resolve()` from `$app/paths` receives a route ID and its parameters where it received a pathname
  starting with `/`: `resolve('/storage')` becomes `resolve('/(admin)/storage')`, and
  `` resolve(`/collections/${collectionId}`) `` becomes
  `resolve('/(admin)/collections/[collectionName]', { collectionName: collectionId })`. The resolved path
  is the same, and a parameter is inserted as given, as the template literal did; an empty parameter,
  or one starting or ending with `/`, now throws where it produced a malformed path.
- `@vitest/browser/context` becomes `vitest/browser` in the two browser tests.
- No other deprecated API is migrated (§Non-goals).

### 5. The Cloud Run adapter 2.0.0

The adapter follows `@sveltejs/adapter-node` 6.0.1's structure (`index.js`), with these differences:
no `node:http` server, the polka middleware chain of ADP-5, the Functions Framework's `rawBody`, and
the startup environment of ADP-7 and ADP-8.

**The Vite plugin** (`adapter.vite.plugins.post`, applied to `build`):
- `ssr.external`: the `dependencies` of `package.json` in `process.cwd()`, without those matched by
  `config.ssr.noExternal` (string or RegExp rules); `ssr.noExternal: true`.
- `environments.ssr.build.sourcemap: true`.
- `environments.ssr.build.rolldownOptions.input`: `adapter-index` (`src/index.js`), `handler`
  (`src/handler.js`), `adapter-env` (`src/env.js`). `src/index.js` re-exports `handler` from
  `./handler.js`.
- The hand-off specifier `#@genoacms/sveltekit-adapter-cloud-run-functions` is external, with
  `output.paths` mapping it to `../adapter.js`. Chunks from the adapter's own modules are named
  `adapter-[name].js` at the output root, all others `chunks/[name].js`, so the hand-off path holds.

**`adapt(builder)`**, in order:
1. `fs.rmSync(out, { force: true, recursive: true })`.
2. `builder.writeClient(<out>/client<base>)` and `builder.writePrerendered(<out>/prerendered<base>)`,
   with `base = builder.config.paths.base`; `builder.compress` both when `precompress`.
3. `builder.generateServerInstance(<server>/server.js)`, where `<server>` is
   `builder.getServerDirectory()`; then `builder.copy(<server>, <out>/server)`.
4. Write `<out>/adapter.js`, the hand-off module:
   `export { server } from './server/server.js'`, `dir` (its own directory), `base`, `app_path`
   (`builder.getAppPath()`), `prerendered` (`new Set(<builder.prerendered.paths>)`), `origin`
   (`builder.config.paths.origin`, or `undefined`) and `env_prefix`.
5. Write `<out>/index.js` (`export * from './server/adapter-index.js';`) and `<out>/handler.js`
   (`export * from './server/handler.js';`).

`supports: { read: () => true }`. The adapter does not declare `instrumentation` (§Non-goals).

**The handler** imports `server`, `dir`, `base`, `app_path`, `prerendered`, `origin` and `env_prefix`
from the hand-off module. It installs no polyfills: SvelteKit 3 removed
`@sveltejs/kit/node/polyfills`, and `src/shims.js` is deleted (ADP-4, F28; the author's decision of
2026-10-30). `manifest.appPath` (ADP-5's immutable prefix) becomes
`app_path`. It calls `readStartupEnvironment(process.env, env_prefix)` before `server.init`.

**`readStartupEnvironment(env, prefix)`** in `src/request.js`, the one function behind ADP-7 and
ADP-8, returns `{ xffDepth }` and throws, in this order:
1. `prefix + 'ORIGIN'` is a key of `env`: `ORIGIN is no longer read; set the origin at build time with
   paths.origin (the gcp target's origin option)`.
2. With a non-empty `prefix`, a key starting with `prefix` other than `prefix + 'XFF_DEPTH'`: the
   existing `You should change envPrefix (<prefix>) to avoid conflicts with existing environment
   variables — unexpectedly saw <name>`.
3. `parseXffDepth(env[prefix + 'XFF_DEPTH'])`, unchanged.

`src/env.js` keeps only `env(name, fallback)`, reading the prefix from the hand-off module.

**`package.json`**: version `2.0.0`, by the changeset; `files`: `index.js`, `index.d.ts`,
`ambient.d.ts`, `src`; no `build`, `dev` or `prepublishOnly` script; `dependencies`: `@polka/url`,
`sirv` (both from today's devDependencies, now imported from `src` at the user's build), no Rollup
packages; `peerDependencies`: `@sveltejs/kit ^3.0.0`; devDependencies to §6's versions, `vitest`
`^4.1.12`. Core's `adapters` script no longer builds the adapter.

### 8. Core builds from its published package (amendment)

CLI-21 is added to `cli.md`; its text is in that document. pnpm is the installer because its layout
exposes to each package only what that package declares, so it also catches an import of an
undeclared package that npm's hoisting would hide.

`packages/core/vite.config.ts` keeps its imports of `@sveltejs/kit/vite`, `@sveltejs/kit` (type),
`@sveltejs/vite-plugin-svelte`, `@tailwindcss/vite`, `@genoacms/config/vite` and
`@genoacms/config/load`, the `resolveKitTarget` call and `kitPlugins`, and exports:

```ts
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [genoa(), tailwindcss(), kitPlugins],
  ssr: { noExternal: [] },
  server: { fs: { allow: ['../..'] } },
  optimizeDeps: { include: [] }

```

It imports nothing from `vitest`, `@vitest/*` or `node:url`, and does not read `VITEST`.

`packages/core/vitest.config.ts` holds what `vite.config.ts` held for Vitest, unchanged in meaning:

```ts
import { playwright } from '@vitest/browser-playwright'
import { configDefaults, defineConfig, mergeConfig } from 'vitest/config'

import { fileURLToPath } from 'node:url'
```

`packages/core/package.json` gains `"peerDependencies": { "@sveltejs/kit": "^3.1.1" }` and keeps
`@sveltejs/kit` `^3.1.1` in `dependencies`.

## Non-goals

- `packages/docs`: sveltepress is not known to support SvelteKit 3. It stays on SvelteKit 2.
- Deprecated APIs that still work in SvelteKit 3: `invalidateAll` (8 call sites), `error(status,
  { message })`, `$env/*`, the `Server` class. They are a later change, with a warning each.
- `trustedOrigins` for CSRF.
- OpenTelemetry instrumentation in the Cloud Run adapter (`supports.instrumentation`).
- Remote functions: they stay `experimental.remoteFunctions: true`, unchanged.
- Moving `.svelte-kit/` or Vite's temporary files out of the installed core (D7's cost).
- Any statement of core's architecture documents: none names a changed API.
- Amendment: moving `vitest` or any other package between core's `dependencies` and `devDependencies` (`build.md` U6); a `files` field for core or the CLI; deploying to GCP or AWS from the packed packages; npm and yarn installs; `genoa dev` and `genoa rotate-root`, which load the same `vite.config.ts` as `build`.

## Tests

## Critique

**Pros**
- GenoaCMS runs on a supported SvelteKit, with one config file fewer and one origin mechanism on
  every target.
- The Cloud Run adapter loses Rollup, its `files/` build step and a second bundling pass. A fresh
  checkout can build the `gcp` target without building the adapter first (F17).
- A leftover `ORIGIN` fails loudly on GCP instead of silently serving the wrong origin.
- `resolveKitTarget` keeps all deployment knowledge in descriptors: core's Vite config stays free of
  target names.
- Amendment: the build config holds nothing a build does not need, and CLI-21's test builds the
  exact artifacts `changeset publish` uploads, installed as users install them, so it also catches a
  missing file, an undeclared import or an unbuilt `dist/`.

**Cons & trade-offs**
- One large change across about 330 files, most of them the `$lib` migration. Review is of the
  specification and the tests, not that diff.
- Breaking for every user of core on Node 20, and for users of the Cloud Run adapter outside
  GenoaCMS, who must move `ORIGIN` into `paths.origin`.
- `ssr.external` is computed from `package.json` in `process.cwd()`, as before; that this is core's
  `package.json` still depends on R1.
- Two copies of the adapter-node 6 idiom (its plugin and the Cloud Run adapter's) now have to follow
  upstream changes by hand.
- The Svelte libraries in core's `dependencies` are now bundled: the server output grows, and an
  update of one of them needs a rebuild, as any bundled code does.
- Amendment: two config files, and a test option placed in `vite.config.ts` is ignored by Vitest
  without an error. The peer makes package managers install or check `@sveltejs/kit` against the
  project. CLI-21's test installs from the registry and builds core twice: minutes, with network.

**Blindspots & missed edge cases**
- S-1 (adapter runtimes stay external, loaded by a non-literal import) was verified under Rollup.
  Rolldown may treat `import(/* @vite-ignore */ s)` differently; §Verification repeats it, but a
  failure there reopens D4, not only this RFC.
- `svelte-check` and `eslint-plugin-svelte` must find SvelteKit 3's config without
  `svelte.config.js`. If the released `svelte-check` cannot, `check` loses route types: a discovery,
  not a reason to restore the file.
- Vitest 4 changes browser mode, mocking of ESM and some defaults. Core's 3133 tests may fail for
  reasons unrelated to SvelteKit; each is a finding before code changes an assertion.
- `fail()` statuses are now sent in enhanced form responses, and `cookies.set` defaults its path to
  `/`. Core's forms read `result.type`, and its cookie sets a path, so neither is expected to change
  behavior. Neither is tested here.
- The `adapter-node` target's `origin` is optional, and without it a plain-HTTP server fails every
  form post with a CSRF 403 (F30). `validate` cannot tell, so the failure shows only at runtime.
- That the handler and the app share one copy of SvelteKit's runtime is a property of the single
  pass, not tested: no observable behavior distinguishes it, short of asserting SvelteKit's
  internal file names.
- Core's Playwright suite, which needs GCP, is not in §Verification; it runs in CI on `main`.
- An undeclared variable read from `$env/dynamic/private` is `undefined` without an error (F29).
  `demo-svelte` and the fixture declare theirs; any other consumer migrating a SvelteKit app has to
  find its own, and no check here would notice one it missed.
- Without polyfills, the Cloud Run adapter needs a runtime with the `crypto` and `File` globals. The
  gcp target deploys `nodejs22`; the adapter's own `engines` do not say so.
- Amendment: CLI-21 runs no GCP or AWS deploy, no `genoa dev`, and only pnpm 10.6.1, the
  repository's version; the reporting user runs pnpm 12. The test packs the working tree, so a stale
  local `dist/` tests stale code.
- Amendment: that this RFC shipped a release no user could build shows §Verification ran only in
  place; the "Live" deploy was from the repository, not from an install.
